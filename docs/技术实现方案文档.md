## 1. 文档目标

本文档基于 [`requirements-spec.md`](./requirements-spec.md) 与 2026-03-15 前后核验的 GitHub、OpenRouter、Next.js、Prisma 官方资料，给出 GitTrans SaaS MVP 的可落地技术实现方案。

本文档只覆盖 MVP 最小可行闭环，不扩展图片翻译、Notebook、人工审校工作台、团队协作权限、多格式翻译等后置能力。

---

## 2. 已确认的关键决策

### 2.1 产品边界

- 仅支持 GitHub 仓库作为内容源。
- MVP 首发仅支持 GitHub 公共仓库。
- 仅翻译 Markdown / README 文档。
- 输出固定写入 `translations/{lang}/...`。
- 程序只创建或更新 PR，不直接写默认分支。

### 2.2 认证与集成

- 必须采用 GitHub App。
- 登录与仓库授权统一走 GitHub App 体系：
  - 用户身份识别使用 GitHub App 的用户授权流。
  - 仓库访问与写回使用 GitHub App installation access token。
- 不单独注册 GitHub OAuth App。

### 2.3 技术栈

| 层级 | 方案 |
|---|---|
| 前端 / Web 框架 | Next.js 15 + App Router + TypeScript 5 |
| UI | Tailwind CSS + shadcn/ui |
| 数据库 | MySQL 8.0+ |
| ORM | Prisma 6+ |
| GitHub SDK | Octokit |
| 后台任务 | MySQL 任务表 + 独立 Worker 轮询执行 |
| AI 接入 | OpenRouter |
| 容器化 | Docker / Docker Compose |
| 部署形态 | Web 容器 + Worker 容器 + MySQL 容器 |

### 2.4 密钥策略

- P0：支持平台托管 OpenRouter Key。
- P1：支持用户自带 OpenRouter Key。
- 平台托管模式必须具备限流、配额和滥用防护。

### 2.5 PR 策略

- 每个仓库维护一个长期存在的翻译分支。
- 每个仓库维护一个持续更新的翻译 PR。
- 后续任务优先更新已有 PR，不重复创建多个 PR。

### 2.6 推荐项目结构

推荐采用单仓结构，Web 与 Worker 共用领域层和集成层代码：

```text
gittrans/
├── src/
│   ├── app/                     # Next.js App Router 页面与 API
│   ├── components/              # UI 组件
│   ├── modules/                 # 业务模块
│   │   ├── auth/
│   │   ├── github/
│   │   ├── repos/
│   │   ├── translation/
│   │   ├── tasks/
│   │   └── billing/
│   ├── lib/                     # 基础设施封装
│   │   ├── db/
│   │   ├── crypto/
│   │   ├── queue/
│   │   ├── logger/
│   │   └── rate-limit/
│   ├── worker/                  # Worker 入口与任务执行器
│   ├── types/                   # 类型定义
│   └── config/                  # 常量与受控配置
├── prisma/

│   └── migrations/
```

这样做的好处：

- Web 与 Worker 可共享 GitHub / OpenRouter / 数据模型代码。
- MVP 阶段避免多仓带来的发布与版本协调成本。
- 后续若拆服务，仍可按模块逐步抽离。

## 3. 方案总览

GitTrans MVP 采用“单代码仓单体应用 + 独立 Worker”的架构，而不是多微服务拆分。

这样做的原因：

- MVP 复杂度主要来自 GitHub 集成、异步翻译编排、幂等与 PR 写回，不来自服务拆分。
- Next.js 适合承载 UI、配置接口、GitHub 回调与只读查询接口。
- 翻译任务、README 导航更新、PR 写回属于长任务和外部 I/O 密集任务，应从 Web 请求生命周期中解耦。
- MySQL 任务表足以支撑 MVP 阶段的任务调度和恢复，不必一开始引入 Redis。

系统由三个运行单元组成：

1. `web`
2. `worker`
3. `mysql`

## 5. 核心模块设计

## 5.1 账户与 GitHub 集成模块

职责：

- 处理 GitHub App 用户授权登录。
- 处理 GitHub App 安装回调。
- 建立用户与 GitHub 账号映射。
- 建立仓库与 GitHub installation 映射。

实现要点：

- 使用 GitHub App 用户授权流获取用户身份，不单独引入 OAuth App。
- 使用 App 私钥生成 JWT，再换取 installation access token。
- installation token 只做短期缓存，不做长期持久化。
- 用户 token 只用于“识别用户是谁”和“确认用户能看到哪些安装/仓库”；仓库读写统一走 installation token。

推荐原因：

- 符合 GitHub 当前官方更推荐的 GitHub App 模式。
- 权限细粒度更高。
- 更适合组织用户授权仓库。
- 符合后续从公共仓库扩展到私有仓库的演进路径。

## 5.2 仓库接入与配置模块

职责：

- 展示用户可访问的 GitHub App 安装和仓库。
- 导入目标仓库。
- 配置基准分支、基准语言、目标语言、翻译范围、ignore 规则、模型。

配置来源分层：

1. 数据库中的平台配置
2. 仓库中的 `.gittrans.yml`
3. 仓库中的 `.github-global-ignore`

建议规则：

- UI 保存时以平台数据库为主数据源。
- Worker 在执行任务前将最新配置同步写回仓库配置文件。
- 若检测到仓库中的配置文件被手工修改，则在下一次仓库详情页加载时触发同步解析并刷新 UI。

## 5.3 翻译任务编排模块

职责：

- 创建全量翻译任务。
- 创建增量翻译任务。
- 追踪每个文件、每个语言的执行进度。
- 支持失败重试和幂等。

设计原则：

- 所有翻译都异步执行。
- 同一仓库同一基准分支同一时刻只允许一个运行中的翻译任务。
- Worker 通过数据库锁定任务，防止重复领取。

## 5.4 README 导航处理模块

职责：

- 在 README 中插入或更新多语言导航区。
- 保证多次执行不重复插入。
- 只生成已成功产出的语言链接。

MVP 采用“标记块优先 + 规则插入 + AI 兜底”的方案。

推荐标记块：

```markdown
<!-- gittrans:lang-switch:start -->
## 🌐 Translations
[English](./translations/en/README.md)
<!-- gittrans:lang-switch:end -->
```

处理规则：

1. 若 README 已存在上述标记块，只更新块内内容。
2. 若不存在标记块，优先插入到标题与简介之后。
3. 若存在目录区，则插入到目录之前。
4. 若规则无法稳定命中，再调用模型做一次位置判断。

这样能避免完全依赖模型判断导致的位置漂移与重复插入。

## 5.5 GitHub 写回与 PR 模块

职责：

- 创建或复用翻译分支。
- 批量写入翻译文件。
- 删除被源文件删除后对应的译文文件。
- 创建或更新翻译 PR。

关键决策：

- 不采用逐文件 Contents API 更新作为主方案。
- 采用 Git Data API 批量写回：
  - 读取基准分支最新 commit/tree
  - 为变更文件创建 blobs
  - 基于 base tree 构造新 tree
  - 创建 commit
  - 更新翻译分支 ref

理由：

- 多文件任务只产生一次 commit，更干净。
- 降低同一路径并发更新冲突风险。
- 更适合 README + 多语言文件同时更新。

## 5.6 会话与访问控制模块

职责：

- 维护 GitTrans 登录态。
- 校验用户对仓库、任务、设置项的访问权限。
- 区分“当前登录用户”与“GitHub App installation 所代表的仓库操作身份”。

建议策略：

- Web 层使用安全会话 Cookie 维护登录态。
- 所有仓库和任务查询都基于 GitTrans 内部用户 ID 做归属校验。
- 仓库写回不以用户会话身份执行，而以 installation token 执行。

这样可以避免把“用户能登录平台”和“应用能操作仓库”混成同一凭据模型。

## 5.7 文件树选择与配置同步模块

职责：

- 获取仓库文件树。
- 可视化展示 Markdown 文件。
- 保存 include / ignore 配置。
- 反映仓库中 `.gittrans.yml` 与 `.github-global-ignore` 的最新状态。

推荐行为：

- UI 文件树只展示可翻译候选与关键目录，不展示全部隐藏目录。
- 对 ignore 命中的文件以灰态或禁用样式显示。
- 保存配置时先写数据库，再由 Worker 在任务开始前写回仓库配置文件，避免每次配置保存都立即触发远端写入。

## 6. GitHub App 设计

## 6.0 GitHub App 注册配置建议

建议在 GitHub App 中配置如下字段：

| 配置项 | 建议值 |
|---|---|
| App Name | GitTrans |
| Homepage URL | `https://your-domain` |
| Callback URL | `https://your-domain/api/auth/github/callback` |
| Setup URL | `https://your-domain/dashboard` |
| Webhook URL | `https://your-domain/api/github/webhooks` |
| Webhook Secret | 平台生成的随机高强度密钥 |

说明：

- `Callback URL` 用于 GitHub App 用户授权回调。
- `Setup URL` 用于安装完成后跳回 GitTrans 仪表盘。
- `Webhook URL` 只接收 GitHub App 相关事件，不复用其他业务 webhook。

## 6.1 推荐权限

MVP 最小权限建议如下：

| 权限 | 级别 | 用途 |
|---|---|---|
| Metadata | Read | 读取仓库基础信息 |
| Contents | Read & Write | 读取 Markdown、配置文件，写入翻译分支内容 |
| Pull requests | Read & Write | 创建和更新翻译 PR |

按需可选权限：

| 权限 | 级别 | 何时需要 |
|---|---|---|
| Issues | Write | 需要在 PR 留评论时 |
| Checks | Write | 需要向 PR 回传检查状态时 |

MVP 不建议申请的权限：

- Administration
- Actions
- Secrets
- Members
- Discussions

## 6.2 推荐订阅事件

MVP 建议订阅以下事件：

| 事件 | 用途 | MVP 优先级 |
|---|---|---|
| Installation | 记录安装/卸载状态 | P0 |
| Installation repositories | 仓库授权范围变化 | P0 |
| Push | 基准分支变更触发增量同步 | P1 |
| Pull request | 感知现有翻译 PR 状态变化 | P1 |

说明：

- Webhook 不是独立权限，而是事件订阅。
- 是否能订阅某事件，与对应权限是否充分有关。
- 即使订阅 `push`，也不能只依赖 webhook payload 内的 commit 列表作为最终变更依据。

## 6.3 登录与授权流程

最终采用以下方案：

```text
用户点击“使用 GitHub 登录”
  -> 跳转 GitHub App 用户授权
  -> 回调后建立 GitTrans 用户会话
  -> 展示用户可见的 App installations
  -> 用户选择安装或已有安装
  -> 选择仓库导入
```

该流程的优点：

- 登录和仓库授权都在 GitHub App 体系内。
- 少一个 OAuth App 配置与维护面。
- 更符合 GitHub 当前官方推荐。

## 6.4 关键 GitHub API 使用清单

MVP 中建议明确封装以下 GitHub 能力：

| 能力 | 主要用途 |
|---|---|
| App JWT / installation token | 安装级认证 |
| List user installations | 展示用户可见安装 |
| List installation repositories | 展示可导入仓库 |
| Get tree / get contents | 读取文件树与配置文件 |
| Compare commits | 增量变更检测 |
| Create ref / update ref | 创建和更新翻译分支 |
| Create blob / tree / commit | 批量写回翻译文件 |
| Create / get / update pull request | 管理长期翻译 PR |

建议做法：

- 将这些能力集中封装在 GitHub 集成层，不让页面层直接拼装 GitHub 请求。
- 所有 GitHub 调用统一附带 `request_id` 与仓库上下文日志，方便排障。

## 7. 仓库读取与文件发现

## 7.1 文件树获取策略

优先方案：

- 调用 Git Trees API 递归获取仓库树。

降级方案：

- 如果响应被截断或仓库规模超过递归树响应限制，则按目录分层读取。

原因：

- GitHub 官方对递归树返回数量和响应体大小有限制。
- 对于教程型文档仓库，递归树通常足够；对异常大的仓库必须有降级策略。

## 7.2 可翻译文件筛选规则

候选文件必须同时满足：

1. 位于 include 范围内
2. 未被 `.github-global-ignore` 命中
3. 扩展名属于支持集合
4. 不在 `translations/` 输出目录下

推荐支持扩展名：

- `.md`
- `.mdx` 可选，若首版要控范围则先只做 `.md`

建议：

- 首版只支持 `.md`
- `.mdx` 放到 P1，避免 JSX/组件语法破坏

## 8. 翻译执行设计

## 8.1 全量翻译流程

```text
手动触发全量翻译
  -> 读取基准分支 HEAD
  -> 解析仓库配置
  -> 枚举待翻译 Markdown 文件
  -> 逐语言生成翻译任务项
  -> 调用 OpenRouter 进行翻译
  -> 生成 translations/{lang}/...
  -> 更新 README 导航
  -> 批量提交到翻译分支
  -> 创建或更新 PR
  -> 记录成功同步的 HEAD SHA
```

## 8.2 增量翻译流程

```text
手动触发增量翻译 / Webhook 触发
  -> 获取 lastSyncedSha 与 currentHeadSha
  -> 调用 Compare API 或 commits diff
  -> 得到真实变更文件列表
  -> 过滤出受支持 Markdown 文件
  -> 对新增/修改文件重翻译
  -> 对删除文件同步删除 translations 下对应译文
  -> 更新 README 导航
  -> 批量提交到翻译分支
  -> 更新已有 PR
  -> 更新 lastSyncedSha
```

## 8.3 单文件翻译策略

推荐处理规则：

- 保留代码块原样，不翻译 fenced code block 内容。
- 保留链接 URL、图片 URL、HTML 注释、frontmatter 键名。
- 标题、正文、列表、表格内容进入翻译。
- 对超长文件按标题块切分，避免单次 token 过大。

MVP 建议切分单位：

- 一级标题到一级标题
- 若区块仍过大，再按二级标题切分
- 若仍过大，再按字符数或 token 近似值切片

## 8.4 模型调用策略

MVP 用户只选择一个默认模型。

平台内部保留两种调用模式：

1. 普通单模型翻译
2. 平台托管模式下的预置 fallback

推荐首版只开放单模型翻译，fallback 先只做平台内部容错，不暴露复杂配置。

## 8.5 翻译 Prompt 与内容保护策略

MVP 虽然不做复杂翻译记忆，但必须统一翻译约束，避免文档结构被模型破坏。

系统 prompt 级规则建议固定包括：

- 保留 Markdown 层级结构。
- 不翻译 fenced code block、inline code、URL、文件路径、变量名、命令名。
- 保留 HTML 标签和属性。
- 保留 frontmatter 键名。
- 输出仅返回译文正文，不附加解释。

额外约束建议：

- 对 README 和普通文档使用两套轻微差异化 prompt。
- README prompt 强调保留徽章、项目链接、目录结构和导航标记。
- 普通文档 prompt 强调段落一致性和术语稳定性。

这部分虽然属于实现细节，但直接决定 MVP 翻译结果是否可合并。

## 9. OpenRouter 集成设计

## 9.1 接口使用

主接口：

- `POST /api/v1/chat/completions`

辅助接口：

- `GET /api/v1/models`
- `GET /api/v1/key`

建议请求头：

- `Authorization: Bearer <OPENROUTER_API_KEY>`
- `Content-Type: application/json`
- `HTTP-Referer`
- `X-Title`

说明：

- `HTTP-Referer` 与 `X-Title` 不是强制项，但官方建议可用于应用标识。
- 平台托管模式建议统一带上 GitTrans 自身标识。

## 9.2 模型选择策略

平台维护一份 allowlist，而不是直接展示 OpenRouter 所有模型。

每个模型记录以下能力标签：

- `modelId`
- `displayName`
- `maxContext`
- `supportsStructuredOutput`
- `costTier`
- `qualityTier`
- `enabled`

推荐首批 allowlist 只保留 3 到 5 个模型。

## 9.3 平台托管 Key 与用户自带 Key

调用顺序建议：

1. 若仓库配置存在用户自带 Key，则优先使用用户 Key
2. 否则使用平台托管 Key

安全要求：

- 所有 Key 加密存储
- 应用进程启动时加载主加密密钥
- 数据库只保存密文和元数据，不保存明文

## 9.4 速率限制与配额

平台托管模式必须至少支持以下限制：

| 维度 | 建议限制 |
|---|---|
| 未认证用户 | 不允许执行翻译 |
| 单用户每日任务数 | 限制 |
| 单用户每日 token/字符额度 | 限制 |
| 单仓库并发任务数 | 1 |
| 全局并发翻译数 | 限制 |
| 单 IP 触发频率 | 限制 |

推荐实现：

- Web 层限流：按用户 ID + IP 做请求级限流
- Worker 层配额：按用户、仓库、模型核减额度
- 管理后台可调整额度

## 10. 任务队列与 Worker 设计

## 10.1 为什么不用纯内存队列

纯内存队列在 Docker 重启、容器迁移、进程异常退出后会丢任务，不适合作为 MVP 的可靠实现。

因此推荐采用：

- MySQL 持久化任务表
- Worker 轮询领取
- 行级锁防重

## 10.2 任务表模型

建议核心字段：

| 字段 | 说明 |
|---|---|
| id | 任务 ID |
| repo_id | 仓库 ID |
| type | full / incremental / retry |
| trigger_source | manual / webhook / system |
| status | pending / running / succeeded / failed / cancelled |
| priority | 优先级 |
| payload_json | 执行参数 |
| progress_total | 总文件数 |
| progress_done | 已完成文件数 |
| started_at | 开始时间 |
| finished_at | 结束时间 |
| lock_owner | 当前 worker 标识 |
| lock_expires_at | 锁超时时间 |
| error_summary | 错误摘要 |

## 10.3 Worker 领取机制

推荐基于 MySQL 8 的事务与行锁实现：

- 轮询待执行任务
- 通过事务锁定一条可执行任务
- 更新为 `running`
- 设置 `lock_owner` 和 `lock_expires_at`
- 执行完毕后更新状态

异常恢复：

- 定时扫描超时锁
- 将超时 `running` 任务重置为 `pending` 或 `failed`

## 10.4 子任务粒度

一条主任务下拆分子项：

- 以 `文件 x 语言` 作为最小执行单元
- 记录单项成功或失败
- 单项失败不直接让整个主任务立即失败

## 10.5 任务进度推送

MVP 推荐使用 Server-Sent Events 或短轮询，而不是 WebSocket。

推荐原因：

- 任务进度是服务端单向推送场景。
- SSE 实现和运维复杂度低于 WebSocket。
- 在 Docker 单体部署下更容易落地。

建议接口：

- `GET /api/tasks/:id/progress`

建议返回内容：

- 主任务状态
- 总文件数 / 已完成数 / 失败数
- 当前语言
- 当前文件
- PR URL

若首版不做 SSE，也应至少保留统一的轮询接口契约。

## 13. API 与页面设计

## 13.1 页面

| 页面 | 作用 |
|---|---|
| `/` | 首页与登录入口 |
| `/dashboard` | 仓库列表 |
| `/repo/[id]` | 仓库详情 |

| `/task/[id]` | 任务详情 |

## 13.2 关键接口

| 接口 | 作用 |
|---|---|
| `GET /api/auth/github/start` | 发起 GitHub App 用户授权 |
| `GET /api/auth/github/callback` | GitHub 回调 |
| `POST /api/github/webhooks` | 接收 GitHub Webhook |
| `GET /api/repos` | 仓库列表 |
| `POST /api/repos/import` | 导入仓库 |

## 13.3 接口设计约定

所有内部 API 建议统一以下规则：

- JSON 返回结构统一包含 `success`、`data`、`error`、`requestId`
- 所有写接口做参数校验
- 所有任务创建接口返回任务 ID，而不是同步等待翻译完成
- 任务详情接口返回主任务 + 子任务汇总，不直接返回全文翻译结果

推荐错误码语义：

| 状态码 | 含义 |
|---|---|

| `403` | 无仓库访问权限 |
| `404` | 仓库或任务不存在 |
| `409` | 仓库已有运行中任务 |
| `429` | 触发限流或额度不足 |
| `500` | 系统内部错误 |

## 14. 幂等、并发与一致性设计

## 14.1 Webhook 幂等

使用 GitHub webhook delivery id 去重。

规则：

- 同一个 delivery id 只处理一次
- 重复请求直接返回成功，避免 GitHub 无限重试

## 14.2 仓库级互斥

同一仓库同一基准分支只允许一个运行中任务。

原因：

- 避免两个任务同时改写同一翻译分支
- 避免 PR 内容来回覆盖

## 14.3 PR 一致性

规则：

- 先查数据库是否有 `current_pr_number`
- 若有，则校验 PR 是否仍存在且未关闭
- 若已关闭，重新创建一个新的翻译 PR，并更新数据库

## 15. 安全设计

## 15.1 密钥与凭据

必须加密保存：

- GitHub App 私钥
- OpenRouter 平台托管 Key
- 用户自带 OpenRouter Key

推荐方案：

- 应用层使用 `AES-256-GCM`
- 主密钥通过环境变量注入
- 数据库保存密文、key version、created_at

## 15.2 GitHub Webhook 安全

必须执行：

- 校验 `X-Hub-Signature-256`
- 校验 payload 原文 HMAC
- 拒绝无效签名请求

## 15.3 平台滥用防护

至少实现：

- 登录后才能导入仓库和触发翻译
- 单用户频率限制
- 平台托管 Key 配额限制
- 单仓库串行执行
- 失败重试次数限制

## 16. Docker 与部署设计

## 16.1 部署形态

推荐首版部署为 Docker Compose：

```text
services:
  web
  worker
  mysql
```

可选：

- `nginx` 或 `caddy` 作为反向代理

## 16.2 容器职责

### `web`

- Next.js 生产服务
- 页面渲染
- API
- GitHub 回调
- Webhook 接收

### `worker`

- 轮询任务
- 执行翻译
- 写回 GitHub
- 任务恢复与超时清理

### `mysql`

- 核心业务数据库

## 16.3 环境变量

建议至少包括：

- `APP_BASE_URL`
- `DATABASE_URL`
- `APP_ENCRYPTION_KEY`
- `GITHUB_APP_ID`
- `GITHUB_APP_CLIENT_ID`
- `GITHUB_APP_CLIENT_SECRET`
- `GITHUB_APP_PRIVATE_KEY`
- `GITHUB_WEBHOOK_SECRET`
- `OPENROUTER_PLATFORM_API_KEY`
- `SESSION_SECRET`

建议再补充：

- `NODE_ENV`
- `LOG_LEVEL`
- `WORKER_POLL_INTERVAL_MS`
- `TASK_LOCK_TIMEOUT_MS`
- `RATE_LIMIT_WINDOW_MS`
- `RATE_LIMIT_MAX_REQUESTS`

## 16.4 部署建议

- Next.js 按官方 self-hosting + Docker 方式构建
- Web 与 Worker 使用同一代码仓、不同启动命令
- 数据迁移在发布流程中执行 `prisma migrate deploy`

## 16.5 启动命令建议

建议在同一代码仓中定义两个启动入口：

- `web`: 启动 Next.js production server
- `worker`: 启动任务轮询与执行进程

Docker 层建议：

- `web.Dockerfile` 与 `worker.Dockerfile` 共享基础镜像层
- 通过不同 `CMD` 启动不同进程
- 避免在一个容器里用进程管理器同时跑 web 和 worker

## 20. 主要风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| GitHub API 限流 | 仓库读取或写回失败 | 缓存安装信息，减少无效 API 调用，任务退避重试 |
| OpenRouter 限流或费用异常 | 任务失败或平台成本上升 | 用户级额度、平台级额度、失败重试和熔断 |
| README 插入位置不稳定 | 导航区混乱 | 标记块优先，规则插入，AI 只兜底 |
| 任务执行中容器重启 | 任务丢失 | 使用 MySQL 持久化任务表和超时恢复 |
| 大文件翻译超时 | 任务耗时过长 | 按标题分块、限制单文件大小、分段重试 |
| 翻译分支被人工改动 | PR 状态异常 | 每次写回前重新校验 head/base，必要时重新生成分支 |

## 21. 最终推荐结论

GitTrans MVP 的推荐落地方案是：

- GitHub 侧统一采用 GitHub App，而不是 GitHub OAuth App
- Web 层使用 Next.js 15
- 数据层使用 MySQL 8 + Prisma
- 队列层使用 MySQL 持久化任务表 + 独立 Worker，而不是首版引入 Redis
- AI 层通过 OpenRouter 接入，平台维护 allowlist
- 部署层使用 Docker / Docker Compose
- 仓库写回固定采用“长期翻译分支 + 长期翻译 PR”

这套方案满足以下目标：

- 实现复杂度在 MVP 可控范围内
- 符合 GitHub 当前官方推荐的 App 模式
- 兼顾平台托管 Key 与用户 BYOK 的演进空间
- 可以从公共仓库平滑扩展到私有仓库和更强的任务调度体系
